# 官方 QQ 机器人通道接入预案（第二会话源）

> 2026-11-14 立项记录。动机：非官方协议端生态全面收缩（SnowLuma 转私 11-10、
> NapCat 终结 11-12、Lagrange.OneBot 消失 11-13，见
> `SnowLuma转私事件与协议端预案.md`）后，本地 SnowLuma 2.2.1 成为实质孤品；
> 而官方侧在 2026 年密集开放（个人创建通道全量 03-07、群主动推送恢复 06-22、
> DSH 官方插件 08-15）。本预案评估把**官方机器人**作为鹊桥的**并行第二会话源**
> 接入——不是替换 SnowLuma（替换路线的「形态不兼容」判断维持不变），而是
> 给孤品单点故障加一条零风险对冲，同时复用鹊桥全部既有资产。

## 一、与既有决策的关系（先读这节）

`SnowLuma转私事件与协议端预案.md` 对官方 Bot API 的判定——「换端成本高、
形态不兼容、不能当群友聊天」——针对的是**换端/替换**路线，本预案不推翻：

| 路线 | 判定 | 依据 |
|---|---|---|
| 官方通道**替换** SnowLuma（全迁移） | ❌ 维持否决 | bot 身份暴露（无仿真形态）、无戳一戳/表情回应/转发解析/群历史，产品本体（README L3）不成立 |
| 官方通道作为**并行第二会话源** | ✅ 本预案 | 资产复用（人格卡/记忆/黑话/表情包/调度/控制台全在决策层，与通道无关）；孤品失效日不再是「项目归档」绝路 |

对 EOL 决策树的修订：`SnowLuma转私事件与协议端预案.md` §3.5 的失效日
序列（存量 NapCat → 活跃 fork → 归档）在第 2、3 步之间插入
「**降级到官方通道保底**：仿真形态退场，被动问答/命令能力保留，桥与全部
资产存活」——归档从唯一结局降为最后手段。

## 二、平台事实核验（2026-11-14 检索，出处见文末）

| 事实 | 内容 | 性质 |
|---|---|---|
| 个人准入 | 个人主体实名后可建 5 个机器人；机器人只能被加进**自己是群主/管理员**的群；公开使用仅企业主体 | 官方 FAQ |
| 群消息可见性 | 默认仅 `GROUP_AT_MESSAGE_CREATE`（@ 消息）；群主在机器人资料卡开启「获取群内全部消息」后推送全量 `GROUP_MESSAGE_CREATE` | 官方 wiki |
| 被动回复 | 群聊 5 分钟窗、每条消息最多回 5 次（msg_id + msg_seq 去重） | 官方 wiki |
| 主动消息 | 单聊 4 条/月/用户（用户可一键拒收）；2025-04-21 曾全面停用，2026-06-22 群场景恢复全量开放（需群主开设置项）；2026-01 单聊新增 30 天互动召回 | 官方文档+行业报道，**以真机实测为准** |
| 无对应 API | 戳一戳、表情回应、合并转发解析、群历史、群成员列表、群资料 | 社区适配器能力边界（Karin/MaiBot） |
| 撤回 | 仅自己发的、2 分钟内 | 同上 |
| 身份体系 | openid（32 位 hex），≠QQ 号、跨应用不互通；换 AppID = 全部 openid 失效 | 官方文档 |
| 传输 | WS 与 Webhook 并存；社区称 WS 停维护推 Webhook，但 2026-10 仍有官方 WS 活跃案例（feely0208/dsh-qq-bridge） | 待 M-O1 实测 |
| 官方 DSH 插件 | `@tencent-connect/dsh-qqbot`（2026-08-15 官宣）：3 步接入、扫码绑定、单聊/群聊、每会话独立记忆、@-only 或 always 模式 | 官方+IT之家 |

**噪声提示**：社区有「群机器人 2025-05 停发」「SDK 停更、文档被删」的说法
（linux.do），与官方 FAQ 及 2026-08 第三方分析矛盾。读法：官方资源已倾斜到
AI bot 新链路（含 dsh-qqbot 插件），传统裸 API 文档在收缩——**鹊桥自研
official crate 走裸 WS/REST，属于官方投入收缩的那条线，接口稳定性风险要在
M-O1 spike 里真机验证后再排后续里程碑**。

## 三、架构：官方通道是「第二会话源」，不是换端

```
                     ┌─ SnowLuma (OneBot WS/HTTP) ── 仿真群友身份 ─┐
群消息 ──┤                                                        ├──→ BridgeEvent ──→ core 决策层（零改动）
                     └─ 官方 Bot (WS) ── og:/op: 会话源 ──────────┘
                                ↑
        BridgeAction::SendMessage / qq_* 工具发送：按 key 前缀路由回各自通道
```

**资产天然共享**（挂在决策层与桥状态，与通道无关）：人格卡 roles/*.md、
长期记忆/黑话/表情包库、唤醒调度与频率护栏、看门狗、控制台、DSH 会话管理、
花费记账。**按通道分叉**的只有：会话 key 前缀（`og:<group_openid>` /
`op:<user_openid>`）、对应 social-v2 会话状态、发送通道与 caps。

**core 零改动验证**（2026-11-14 代码盘点）：`core::action::BridgeEvent` /
`BridgeAction` 类型面不含任何 OneBot 类型（IncomingMessage 的 key/user_id/
message_id 均为 String，openid 直接放得下）；入站归一在 bin
`main.rs`（GroupMessage/PrivateMessage → IncomingMessage），出站收口在
`Executor`（SendMessage，main.rs）与 `tools_api.rs` 的 `onebot` 字段
（4 处 send + 8 处 call）。耦合面完整清单见第六节。

## 四、四层改造（按依赖顺序）

### 4.1 `crates/queqiao-official`（新协议 crate，形态对齐 queqiao-onebot）

- **鉴权**：AppID/AppSecret → access_token（REST OAuth，比 SnowLuma per-account
  双 token 自愈简单）；
- **入站**：订阅 `GROUP_AT_MESSAGE_CREATE` / `GROUP_MESSAGE_CREATE` /
  `C2C_MESSAGE_CREATE`，反序列化为强类型 `OfficialEvent`——沿用红线：
  真实报文样例钉反序列化单测，禁止 Value 裸奔穿透到 core；
- **出站**：`POST /v2/groups/{group_openid}/messages`（群）与
  `/v2/users/{openid}/messages`（单聊）；**被动回复必须带 msg_id**，
  msg_seq 递进去重；5 分钟/5 次窗由 caps 层显式建模（见 4.4）；
- **传输**：WS 优先（家庭部署无公网 HTTPS，Webhook 要挂隧道）；crate 内
  抽 `Transport` trait，Webhook 留备选——官方若真停 WS，切换不动上层。

### 4.2 通道抽象：`PlatformClient` trait（bin 层）

- 抽象位：`Executor.onebot`（SendMessage 动作执行）与 `AppState.onebot`
  （qq_* 工具发送）。按 key 前缀路由：`group:`/`private:` → OneBot client，
  `og:`/`op:` → Official client；
- 与 `SnowLuma转私事件与协议端预案.md` §三的 `onebot_backend` trait
  **会合流**：本 trait 做出来后，「换端」（SnowLuma→NapCat 存量）只是
  OneBot client 的第二实现，抽象成本一次付清；
- 官方通道发送需携带最近入站 msg_id（被动窗）——路由层从该会话
  social-v2 状态取最近一条消息 id 传入。

### 4.3 openid 映射与准入（v1 不做 openid→QQ 号换算）

- 身份即 openid：官方会话的记忆/印象/记账按 openid 记，与 QQ 号体系
  天然隔离（同一群友在两个通道是两个身份——v1 接受，见第七节决策 3）；
- config 新增 `official` 节：`appId` / `appSecret` / `sandbox` /
  `allow.groups: Vec<String>`（group_openid）/ `allow.users: Vec<String>`
  / `enabled: false` 默认关——准入语义复用 deny>allow>空表+allowAllWhenEmpty
  （config.rs conversation_allowed 的官方版重载，拒绝一切非白名单 openid）；
- 控制台加「官方通道」页签：最近收到的 openid 列表 + 一键加白
  （体验优于 MaiBot 的聊天内 /assign_id 绑定命令——鹊桥有 UI）；
- **不做** openid→QQ 号映射表：openid 跨应用不互通且无查询 API，映射只能
  靠群友自报（隐私与准确性双差）；若未来需要跨通道身份合并，等官方
  union_openid 能力成熟再评估。

### 4.4 能力降级矩阵（45 工具 × 官方 caps）

工具执行前查通道 caps；不支持者返回**带解释的 denied**（denied() 帮手与
MCP schema 守护测试均为现成套路）。caps 位图存 OfficialClient，prompt 构造
时注入通道能力说明（AI 不会调不存在的工具）。

| 类别 | 工具 | 官方通道处理 |
|---|---|---|
| ✅ 直接可用 | send_message / reply / send_burst（≤5 条/被动窗，超出的拆下一窗或拒）/ mark_read / memory 全家 / diary / slang / sticker 查询收藏 / wait_for_messages / get_prompt / social_state / report_feedback / list_stickers / get_sticker_image | 原样（发送走 official client） |
| ⚠️ 降级实现 | get_recent_messages / get_unread_messages（仅官方通道自己见过的事件流，无历史回溯）/ get_message_detail / get_message_images（attachments 字段收图）/ get_my_recent_messages / recall（2 分钟窗，API 不同）/ send_voice（富媒体接口形态不同）/ fetch_sticker（入库可用，发送侧仅 URL 图） | caps 标记 + 替代实现，prompt 注入差异说明 |
| ❌ denied | send_poke / react_message / get_forward_msg / get_group_history / get_group_members / get_group_profile / list_groups / get_active_members / get_self_image / send_sticker（除非富媒体传图可覆盖）/ collect_sticker（依赖 QQ 表情元数据） | denied 文案「官方通道不支持该能力」 |
| 🔄 语义重写 | set_wake_config 的主动类触发 / proactive_check 调度 | 官方 key 默认关主动；额度模型见 4.5 |

`qq_speak`（若为发送辅助）与 tablet/pc/browser 域与通道无关，不动。

### 4.5 主动额度模型（官方 key 专用）

- 被动窗内（收到消息 5 分钟、余量 ≥1）正常回复——这是官方通道的主形态；
- 主动消息按「月 4 条/群」硬预算记入 social-v2（per-key 计数器 + 月度重置），
  超预算的 proactive 动作直接吞掉并日志（宁可不说不超发——错误码退避只是
  兜底，前置预算才是正解）；
- 单聊召回（30 天窗）v1 不做——语义与鹊桥唤醒模型差异大，收益低。

## 五、里程碑

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| M-O1 协议 spike | queqiao-official：token + WS + 事件反序列化 + 沙箱群被动回一条 | 沙箱群真机收发冒烟（对齐 onebot_smoke 形态：`official_smoke` example）；同时实测：全量消息事件稳定性、主动额度真实值、WS 存活状态 |
| M-O2 通道路由 | PlatformClient trait + key 前缀路由 + Executor/AppState 双持 | 双通道各自跑通 MessageArrived→decide→SendMessage 闭环；现有测试零回归 |
| M-O3 身份与配置 | official 配置段 + 控制台官方页签 + openid 白名单 | openid 一键加白可用；非白名单 fail-closed |
| M-O4 caps 降级 | 45 工具矩阵 + prompt 能力注入 | 每工具 caps 有守护测试（沿用 schema 守护套路） |
| M-O5 主动预算 | 官方 key 主动额度 + 被动窗利用 | 真机一月内主动消息 0 超发；错误码（召回上限类）退避生效 |

工作量直觉：M-O1~O2 主体（协议客户端比 onebot crate 简单——官方文档完善，
无 token 自愈探测）；M-O3~O5 打磨。**触发条件同 SnowLuma 预案哲学：先 spike
后排期——M-O1 完成且第二节噪声（官方裸 API 收缩）被真机证伪前，M-O2 以后
不排期**。

## 七、产品决策（v1 定案）

1. **双身份同群禁止**：v1 白名单互斥——每个群只走一个通道（配置校验：
   同一 QQ 群号同时出现在 official.allow 与观测名单时告警）。同群双人格
   （一个决策循环、两张嘴，消息流合流进同一 key）留作 v2 实验项；
2. **官方 key 的性格延续**：人格卡/记忆共享意味着官方 bot 与仿真号是
   「同一个人换了躯体」——prompt 注入通道形态说明（你在本群以机器人
   身份在场，群友知道你是 AI）；不装人，装了反而扣信任分；
3. **跨通道身份不合并**：同一群友经两个通道的两份印象/记账并行存在，
   v1 接受（openid 换算无 API，见 4.3）；
4. **日记宿主不变**：diary 的 host 仍是仿真号私聊 key——官方通道不承载
   日记触发（bot 的「私房话」写在仿真号躯体里，语义上也更对）。

## 八、红线补充（动工时并入规格 §五，效力同级）

1. **core 不得依赖通道类型**：BridgeEvent/BridgeAction 类型面禁止出现
   OneBot/Official 具体类型（现状已满足，改动不得回退）；
2. **官方通道 fail-safe**：official crate 任何故障（断流/token 失效/API
   变形）不得拖垮 OneBot 主链路——两通道的连接管理、重连、看门狗探活
   相互隔离；看门狗对 official 通道单列探活项，故障仅告警不重启主桥；
3. **发送路由只认 key 前缀**：任何发送路径（Executor/工具）必须经统一
   路由，禁止工具内直接持 official client 绕过 caps 检查；
4. **主动额度前置**：官方通道主动消息先查本地预算再发，API 错误码退避
   仅作兜底——不依赖平台侧拦截做频率控制。
